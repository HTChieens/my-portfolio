Agent-Native Browser: thiết kế lại trình duyệt web khi người dùng chính là AI agent

Nếu không còn "mắt người" là trung tâm, browser không nên tối ưu cho pixel trước tiên. Nó nên tối ưu cho ý nghĩa, quyền hạn, trạng thái, bộ nhớ và hành động có thể kiểm toán. Trình duyệt mới không phải là Chrome có thêm automation; nó là một môi trường vận hành cho agent trên web.

Tài liệu này thiết kế lại web browser với giả định: người dùng chính không phải human nhìn màn hình, mà là agent cần hiểu trang, điều hướng, đăng nhập, ghi nhớ và thực hiện hành động một cách an toàn. Deliverable gồm ba phần: design manifesto, kiến trúc lõi, và interface dành cho agent kèm ví dụ cụ thể.

1. Design manifesto

Browser hiện tại sinh ra để trả lời câu hỏi: "Trang này trông như thế nào với người dùng?". Agent-native browser phải trả lời câu hỏi khác: "Trạng thái này có nghĩa gì, tôi được phép làm gì, hành động nào có hậu quả gì, và làm sao chứng minh tôi đã làm đúng?".

Nguyên tắc thiết kế

  1. Meaning over pixels: pixel chỉ là một view. Nguồn sự thật cho agent là semantic state tree có intent, role, constraint, data binding và side effect.
  2. Actions over events: agent không nên phải click tọa độ hoặc đoán nút. Trang phải công bố action có kiểu, input schema, effect model, quyền cần có và khả năng undo.
  3. Navigation as task graph: điều hướng không chỉ là URL/back/forward. Nó là đồ thị trạng thái và nhiệm vụ: vào đâu, cần điều kiện gì, rủi ro gì, có thể quay lại ra sao.
  4. Auth is delegation: agent không nên mượn toàn bộ danh tính user. Mỗi phiên cần token ủy quyền có scope, thời hạn, mục đích và policy gate.
  5. Memory is governed: browser cần nhớ việc đang làm, nhưng phải nhớ có nguồn gốc, thời hạn, phạm vi và quyền xóa. Bộ nhớ không được biến thành kho dữ liệu mơ hồ.
  6. Every side effect is auditable: mọi hành động như gửi form, mua hàng, hủy gói, xóa dữ liệu phải có preview, commit record, actor, lý do và log kiểm toán.
  7. Human visibility remains available: không cần eyeballs trong vòng lặp mặc định, nhưng cần render khi debug, khi tranh chấp, khi agent không chắc, hoặc khi user muốn xem lại.
Agent-native không có nghĩa là bỏ HTML/CSS. Nó có nghĩa là không bắt agent hiểu thế giới qua cùng lớp biểu diễn dành cho mắt người. Pixel trở thành một adapter, không phải API chính.

2. Điều gì thay đổi khi không còn eyeballs?

Thành phần Browser cho human Browser cho agent
DOM / Rendering DOM + CSSOM tạo layout, paint, composite để người dùng nhìn và click. Semantic DOM mô tả object, intent, data, constraints, confidence, action bindings. Rendering pixel là optional.
Navigation URL, link, history, back/forward, route trong SPA. Task graph, state transition, deep links theo năng lực, undo theo nghĩa vụ và side effect.
Auth User login, cookie/session, toàn bộ quyền nằm trong browser profile. Delegated agent session: scope cụ thể, time-bound, purpose-bound, approval gate cho hành động nhạy cảm.
Memory Tab state, cache, localStorage, cookies, history. Working memory, site memory, task memory, policy memory, audit memory, tất cả có provenance và isolation.
Action API Click, type, scroll, wait, query selector. List/inspect/preview/commit/undo action có schema, effect model, risk, permissions và result contract.

3. Kiến trúc lõi

Agent-native browser nên được chia thành nhiều tầng rõ ràng. Web engine truyền thống vẫn tồn tại để chạy web thật, nhưng phía trên nó có một lớp diễn giải ngữ nghĩa, một lớp chính sách và một action runtime. 

Web nguồn: HTML, CSS, JS, HTTP, Web APIs
  -> Legacy Web Engine
       - network stack
       - JavaScript runtime
       - DOM/CSSOM compatibility
       - optional renderer
  -> Semantic Extraction Layer
       - semantic state tree
       - form/data binding detection
       - action discovery
       - state and effect inference
  -> Agent Runtime Layer
       - task graph navigator
       - action planner/executor
       - memory vault
       - auth delegation manager
       - policy and approval engine
  -> Agent Interface
       - observe state
       - inspect action
       - preview effect
       - commit action
       - undo/compensate
       - explain/audit

Các module chính

Module Nhiệm vụ Ví dụ output
Semantic State Tree Biến DOM, accessibility tree, schema.org, ARIA, text, network data và app state thành cây ý nghĩa. "Đây là bảng invoices, có 12 dòng, mỗi dòng có action download_pdf."
Action Registry Phát hiện hoặc nhận khai báo action mà site hỗ trợ. "update_billing_address", "cancel_subscription", "export_report".
Effect Modeler Mô tả hậu quả trước khi làm: chỉ đọc, ghi dữ liệu, gửi email, thanh toán, xóa, không thể undo. "Hành động này sẽ đổi địa chỉ billing và gửi email xác nhận."
Task Graph Navigator Điều hướng theo mục tiêu thay vì click từng menu. "Từ dashboard có thể đến invoices bằng state billing.invoices."
Delegated Auth Manager Cấp phiên agent có quyền nhỏ hơn user và gắn với task. "Đọc invoice được, đổi payment method thì cần user approve."
Memory Vault Lưu task state, preference, site map, dữ liệu tạm và audit theo phạm vi. "Đã tải invoice tháng 7, không cần tải lại."
Policy Engine Chặn hoặc yêu cầu phê duyệt dựa trên rủi ro, quyền, chi phí, dữ liệu nhạy cảm. "Không được commit cancel_subscription nếu chưa có approval token."
Visual Adapter Render screenshot khi cần kiểm tra thị giác hoặc debug. "Có modal xác nhận mà semantic layer chưa hiểu chắc."

4. DOM và rendering mới

DOM hiện tại nói nhiều về cấu trúc tài liệu, ít nói về ý định. Agent cần một cây có thể trả lời: node này là gì, liên quan đến dữ liệu nào, có thể làm gì với nó, action nào nguy hiểm, và trạng thái nào là nguồn sự thật.

Semantic node

{
  "node_id": "invoice_row_2026_07",
  "kind": "record",
  "domain_type": "billing.invoice",
  "label": "Invoice July 2026",
  "data": {
    "invoice_id": "inv_2026_07",
    "amount": "128.00",
    "currency": "USD",
    "status": "paid"
  },
  "bindings": {
    "source_dom": "#billing-table tr[data-id='inv_2026_07']",
    "source_endpoint": "GET /api/invoices"
  },
  "available_actions": ["download_invoice_pdf", "view_invoice_detail"],
  "confidence": 0.97
}

Rendering không biến mất, nhưng đổi vai trò

  • Default mode: không cần vẽ toàn bộ trang, chỉ cần chạy JS/app state và xuất semantic state.
  • Verification mode: render ảnh khi semantic extraction chưa chắc hoặc khi cần xác nhận UI thật đang hiển thị gì.
  • Replay mode: render lại phiên làm việc cho human audit: agent đã thấy gì, chọn gì, commit gì.
  • Fallback mode: nếu site không hỗ trợ semantic/action manifest, browser dùng DOM + accessibility tree + vision/OCR như cầu nối tạm.
Browser cho agent vẫn cần tương thích web cũ. Nhưng chuẩn tốt nhất là site tự khai báo semantic/action manifest để agent không phải đoán từ class name, màu nút hoặc vị trí trên màn hình.

5. Navigation trở thành task graph

Với human, navigation là "click Settings rồi Billing rồi Invoices". Với agent, navigation nên là "đưa tôi đến state có capability billing.invoice.list". Đường đi cụ thể có thể thay đổi theo UI, nhưng capability thì ổn định hơn.

Ví dụ task graph

{
  "site": "acme-saas.example",
  "states": [
    {
      "state_id": "dashboard.home",
      "capabilities": ["account.summary", "navigation.search"]
    },
    {
      "state_id": "billing.invoices",
      "capabilities": ["billing.invoice.list", "billing.invoice.download"],
      "requires": ["auth.scope:billing.read"]
    },
    {
      "state_id": "billing.payment_method",
      "capabilities": ["billing.payment_method.view", "billing.payment_method.update"],
      "requires": ["auth.scope:billing.write", "approval:payment_change"]
    }
  ],
  "transitions": [
    {
      "from": "dashboard.home",
      "to": "billing.invoices",
      "method": "internal_route",
      "route": "/settings/billing/invoices",
      "side_effect": "none"
    }
  ]
}

Navigation API

agentBrowser.navigate.toCapability("billing.invoice.list")

Response:
{
  "state_id": "billing.invoices",

6. Auth là ủy quyền có phạm vi

Browser hiện tại thường có cookie mạnh ngang với user. Nếu agent nắm cookie đó, mọi hành động user làm được đều có nguy cơ bị tự động hóa. Agent-native browser cần phiên ủy quyền riêng: làm task nào, được đọc/ghi gì, hết hạn khi nào, hành động nào phải hỏi lại.

Mẫu delegated session

{
  "agent_session_id": "ags_742",
  "human_principal": "user_123",
  "agent_principal": "agent_invoice_helper",
  "purpose": "download_monthly_invoices",
  "expires_at": "2026-08-03T18:00:00+07:00",
  "scopes": [
    "billing.invoice.read",
    "billing.invoice.download"
  ],
  "denied_scopes": [
    "billing.payment_method.update",
    "subscription.cancel"
  ],
  "approval_policy": {
    "read": "auto",
    "download": "auto",
    "send_external": "ask",
    "purchase": "ask",
    "delete": "ask",
    "irreversible": "ask"
  }
}

Auth thay đổi ở cấp sản phẩm

Tình huống Thiết kế agent-native
Agent đọc invoice Cấp scope billing.invoice.read, không cấp quyền đổi billing.
Agent cập nhật địa chỉ billing Cần scope write và preview diff trước khi commit.
Agent hủy subscription Luôn cần human approval vì có side effect lớn và có thể không undo được.
Agent gửi email qua webmail Preview người nhận, subject, body, attachment; commit chỉ sau approval nếu policy yêu cầu.

7. Memory: browser có trí nhớ nhưng phải có luật

Agent làm việc tốt hơn nếu browser nhớ cấu trúc site, trạng thái task, quyết định trước đó và preference của user. Nhưng memory cũng là nơi dễ rò dữ liệu nhất. Vì vậy mỗi mẩu nhớ cần có phạm vi, nguồn, thời hạn và quyền truy cập.

Loại memory Lưu gì Luật an toàn
Working memory Task hiện tại, state đang mở, action đang pending. Xóa khi task kết thúc hoặc user yêu cầu.
Site memory Map capability của website, selector ổn định, lỗi thường gặp. Không lưu dữ liệu cá nhân nếu chỉ cần cấu trúc site.
Task memory Invoice nào đã tải, form nào đã gửi, kết quả từng bước. Gắn với task id và audit log.
Policy memory Giới hạn chi tiêu, hành động cần hỏi, domain bị chặn. User chỉnh được, agent không tự nới quyền.
Audit memory Agent đã quan sát gì, vì sao chọn action, commit lúc nào. Append-only, có retention và xuất báo cáo được.

8. Agent-facing interface

Interface chính không nên là WebDriver kiểu click/type. Nó nên là một API có vòng đời: observe, plan, inspect, preview, commit, verify, undo và audit.

Core API surface

Method Mục đích Ghi chú
observe() Lấy semantic state hiện tại. Trả về state tree, capabilities, pending risks.
navigate.toCapability() Đi tới trạng thái có năng lực cần dùng. Không cần biết menu nằm ở đâu.
actions.list() Liệt kê action agent có thể làm trong state hiện tại. Gồm action site khai báo và action browser suy luận.
actions.inspect() Xem input schema, effect, risk, permission. Không commit gì ở bước này.
actions.preview() Tạo diff/result dự kiến trước khi làm. Cần cho write/delete/purchase/send.
actions.commit() Thực hiện action đã preview hoặc action read-only. Policy engine có thể chặn hoặc yêu cầu approval token.
actions.undo() Quay lại bằng undo thật hoặc compensating action. Không phải action nào cũng undo được.
audit.explain() Giải thích agent đã làm gì và vì sao. Dùng cho user review hoặc compliance.

Action descriptor

{
  "action_id": "download_invoice_pdf",
  "label": "Download invoice PDF",
  "capability": "billing.invoice.download",
  "input_schema": {
    "type": "object",
    "required": ["invoice_id"],
    "properties": {
      "invoice_id": { "type": "string" }
    }
  },
  "effect": {
    "kind": "read_export",
    "side_effects": ["file_download"],
    "external_visibility": "none",
    "undo": "delete_downloaded_file"
  },
  "risk": "low",
  "requires": ["billing.invoice.download"],
  "approval_required": false,
  "result_schema": {
    "file_path": "string",
    "sha256": "string"
  }
}

Action lifecycle

Agent observes state
  -> Browser returns semantic tree and available actions
  -> Agent inspects chosen action
  -> Browser returns schema, effect, risk, permissions
  -> Agent prepares arguments
  -> Browser previews effect
  -> Policy engine approves, denies, or asks human
  -> Agent commits action
  -> Browser verifies result
  -> Memory vault records task state
  -> Audit log records evidence

9. Ví dụ cụ thể 1: tải hóa đơn tháng 7

Với browser truyền thống, agent sẽ vào dashboard, click menu billing, đọc bảng bằng selector, click nút download. Với agent-native browser, agent yêu cầu capability và dùng action có schema.

10. Ví dụ cụ thể 2: đổi địa chỉ billing

Đây là action ghi dữ liệu. Agent không nên gửi form ngay. Nó phải preview diff, kiểm tra policy, sau đó commit nếu phiên có quyền hoặc có approval.

Preview trước khi commit

browser.actions.preview("update_billing_address", {
  "company": "VFS",
  "line1": "Technopark",
  "city": "Hung Yen",
  "country": "VN"
})

{

        "from": "Ha Noi",

11. Ví dụ cụ thể 3: hủy subscription

Hủy gói là ví dụ tốt để thấy khác biệt giữa click automation và action API. Nếu agent chỉ click, nó có thể bị dark pattern, modal giữ chân, hoặc nút có chữ mập mờ làm sai ý định. Action API bắt site khai báo hậu quả.

Inspect action

browser.actions.inspect("cancel_subscription")

Descriptor trả về

{
  "action_id": "cancel_subscription",
  "capability": "subscription.cancel",
  "risk": "high",
  "effect": {
    "kind": "irreversible_or_costly",
    "side_effects": [
      "service_access_ends_at_period_end",
      "team_members_lose_premium_features",
      "retention_email_sent"
    ],
    "undo": "not_guaranteed"
  },
  "requires": [
    "subscription.cancel",
    "approval:human_explicit"
  ],
  "approval_required": true,
  "confirmation_phrase": "Cancel Acme Pro subscription"

Một browser thật cho agent nên coi "hủy", "mua", "gửi", "xóa", "mời user", "đổi quyền", "công khai dữ liệu" là nhóm action cần effect model rõ ràng. Không được để agent suy luận hậu quả từ text trên nút.

12. Kết luận thiết kế

Khi primary user là agent, browser phải đổi từ "máy hiển thị trang" thành "máy vận hành trạng thái và hành động". DOM cần giàu ý nghĩa hơn. Rendering không còn là trung tâm. Navigation phải đi theo capability và task. Auth phải là delegated permission. Memory phải được quản trị như tài sản nhạy cảm. Action API phải typed, inspectable, previewable, committable và auditable.

Câu hỏi thiết kế không còn là "agent có click được nút này không?". Câu hỏi đúng là: "agent có hiểu hành động này nghĩa là gì, có quyền làm nó không, hậu quả là gì, có cần hỏi người dùng không, và sau này có giải thích lại được không?".
